# 10: Manual E2E has no Siri-engine leg (release build, private engine)

**What to build:** `./Scripts/e2e.sh` proves the **release** binary on the private engine too — the same four independent assertions (brand, duration, markers, metadata), plus that the run announced itself as `Engine: siri` — and reports `skip:` rather than `FAIL:` on a Mac with no Siri voice bundle. The default engine's leg stays exactly as it is.

**Blocked by:** 07 (E2E script), 08 (`--engine siri`)

**Status:** resolved

## The gap

`Scripts/e2e.sh` builds `-c release`, runs `"$BIN" "$EPUB" -o "$OUT" 2> "$LOG"` and verifies with `afinfo`/`ffprobe`. It has **no `--engine` and no `--voice` argument anywhere**, so nothing in the project ever runs the release binary through `SiriTTSBridge`:

- the CLI test suite shells out to **`.build/debug/saybook`** (recorded in #07: the release-only `ftyp` bug was invisible precisely because of this), and
- the release test run (`swift test -c release`) compiles the release target but still executes the debug binary.

So `SiriTTSBridge` under `-O`, on a real Book, with real Chapter boundaries, has been verified exactly once, by hand (2026-09-19: `m4bf`, 2:16, 553 KB, `1 ch 22050 Hz aac`). The class of bug this leaves open is the one that bit #07 — a defect that only exists in the shipping configuration.

## Decisions to make (recommendations in brackets)

1. **What does the Siri leg render?** [A small in-repo fixture, e.g. `multi-chapter.epub`, ~17 s of render.] The Siri engine renders at ~8× realtime (#08's measurement) against the public engine's ~40×, so a Siri leg over Alice (~160 min of audio) would add ~20 minutes to a script that today takes ~3. The release-path coverage the ticket wants does not need a 160-minute Book; a `--siri-full` opt-in can run the Book itself for anyone who wants it.
2. **How is "no Siri voice on this Mac" detected?** [Ask the binary, don't re-implement the catalog.] Run `saybook <book> --engine siri --voice __no_such_voice__` and treat an exit 1 whose message contains `no Siri voice bundle is installed` as a skip; any *other* failure stays a FAIL. This reuses `SiriVoiceCatalog` as the single source of truth instead of hard-coding `/System/Library/AssetsV2/com_apple_MobileAsset_UAF_Siri_TextToSpeech/…/gryphon.cfg` into bash — that path is Apple's, and it is the thing most likely to move. Guard the substitution against `set -euo pipefail` (`|| true` on the failing run, per #07's lesson) and keep the skip noisy and explicit.
3. **Cross-engine duration sanity.** [Assert the Siri output's decoded duration is within ~25 % of the Apple leg's for the same Book.] #08 caught the sample-rate question in debug tests (48 kHz mono int16 → 22.05 kHz CAF); on the release path a 2× error is currently silent, and this is a two-line guard that would catch it.

## Comments

- 2026-09-19 (agent): Opened from #08. Note for whoever picks this up: stderr is captured with `2> "$LOG"` (a file), which is *why* the engine's diagnostic torrent never blocked this script — a future change to `2>&1 | tee` would reintroduce the deadlock #08 fixed at the bridge level (`SAYBOOK_SIRI_DIAGNOSTICS=1` reproduces 153 KB of chatter per 6-second Chapter).
- 2026-10-05 (agent): **Implemented as the three recommendations in the ticket body**, all of them. The leg renders the in-repo `multi-chapter.epub` (decision 1); availability is asked of the binary (decision 2) — `--engine siri --voice __no_such_voice__`, exit 1, skip iff the message carries `no Siri voice bundle is installed`, any other exit or message stays a FAIL; and the 25 % cross-engine duration check is in (decision 3). The reference is leg 1's own render when the leg runs the same Book (`--siri-full`), otherwise a ~3 s default-engine render of the fixture. The four assertions were lifted into `assert_audiobook`/`read_expectations`/`run_saybook` rather than copied, so the Siri leg verifies the *same* code paths leg 1 does; `run_saybook` keeps stderr going to a file for the deadlock reason above.
- 2026-10-05 (agent): **Availability is asked of the binary, not of Apple's asset layout in bash**, per decision 2 — which needed a hook to be testable: `SiriVoiceCatalog.assetsRoot` now honours `SAYBOOK_SIRI_ASSETS_ROOT`, the same kind of debugging override as `SAYBOOK_SIRI_DIAGNOSTICS`. Two consequences worth recording. (1) `testSiriEngineWithoutAVoiceFailsAsAUserError` used to `XCTSkip` on any Mac that *has* a bundle, i.e. on the machines its authors used; it now points the catalog at an empty directory and runs everywhere, and it asserts the exact phrase the script's skip keys on, so the bash string and the Swift message can no longer drift apart unnoticed. (2) Verified the probe behaves as the ticket's "any *other* failure stays a FAIL" requires, on both kinds of Mac: bundle present → `Unknown voice … (installed Siri voices: Martha)`, no skip phrase, so the leg runs; bundle absent → `Unknown voice … (no Siri voice bundle is installed on this Mac — …)`, skip fires. Both exit 1 and write no file, so the probe can never leave a stray Audiobook behind. `--voice` is resolved before any work, which is why the probe costs one startup.
- 2026-10-05 (agent): **Cost, measured rather than estimated.** The header said the leg costs ~20 s + ~3 s; it is **~33 s** (fixture path: 38.6 s with the leg, 6.0 s with it skipped, release build cached — the Siri render of the fixture's 2:10 at ~8× realtime is the bulk of it). Corrected in the header. The `--siri-full` ~20 min for Alice remains an **extrapolation** from ~8× against her ~163 min of audio, not a measurement; it is labelled as such in the header.
- 2026-10-05 (agent): **On "runtime unchanged", and why I did not accept the obvious evidence.** The first instinct was to point at the two no-argument Alice runs — 5:51.6 with the Siri leg and 5:45.6 with it skipped, a 6 s difference — as proof. That number is *noise*, not cost: the leg cannot cost 6 s when the same fixture path measures its cost at 32.6 s. So the claim rests on construction instead: leg 1's own code is unchanged (the extraction into helpers is behaviour-preserving; the run, exit-code and output checks and all four assertions produce the same lines in the same order), and the Siri leg runs on the small in-repo fixture rather than the Book, so the only added work on the default path is the availability probe — one binary startup, which is why skipping the leg still takes 6.0 s of it. The no-argument path was nevertheless re-run end to end because the argument parser is new (`for arg in "$@"` with `--siri-full`/`-h`/`-*` rejection and a two-Books guard replacing `$1`), and a download path broken by parsing would be exactly the regression this ticket could introduce.
- 2026-10-05 (agent): Verification on this Mac (bundle present): `./Scripts/e2e.sh <fixture>` both legs green; `--siri-full <fixture>` green with the cross-engine check correctly reusing **leg 1's** duration ("135.676009 s against leg 1's 128.388889 s") and no extra reference render; no-argument Alice path green (163 min of audio, 13 markers, `E2E PASS`); `SAYBOOK_SIRI_ASSETS_ROOT=/nonexistent` prints `skip:` and exits 0. `SAYBOOK_E2E_BIN` rejects a non-executable path. Suite: **167 tests, 0 skipped, 0 failures** in both `swift test` and `swift test -c release` — 0 skipped is itself a change, since the missing-bundle test used to skip on any Mac with a bundle. `bash -n` clean. README's Manual E2E paragraph documents both legs, the two extra assertions, the cost, `--siri-full`, and the skip.
- 2026-10-05 (agent): **Open risk, left deliberately open.** The Siri leg's cross-engine check has 25 % tolerance and this fixture sits at 5.7 %. That is comfortable, but it is one fixture at one rate on one macOS: the check's real purpose is catching a 2× sample-rate error, and it will not notice drift below a quarter, so a subtler future regression (a 15 % shortening, say) passes silently. Accepted — a tighter bound would make the leg fail on Voice and OS variation, which is not a saybook defect, and the ticket asked for a 2×-class guard, not a regression detector. Note also that the leg asserts `Engine: siri` from the *header* line only; it cannot tell the private engine's audio from the public engine's by ear, which is what makes that assertion load-bearing.
