# 08: Private Siri speech engine (`--engine siri`)

**What to build:** A second speech **Engine** behind the existing synthesis seam, so a run can speak a Book with Apple's private on-device Siri engine instead of the public `AVSpeechSynthesizer`. Opt-in (`--engine siri`), default unchanged, same output contract: 22.05 kHz mono CAF per Chapter, so Chapters, Chapter Markers, metadata, resume and the M4B finaliser are untouched. Still offline, still zero third-party runtime dependencies.

**Blocked by:** 01 (synthesis), 02 (resume & markers), 04 (Voice selection), 07 (test suite & README)

**Status:** resolved

- [x] `--engine apple|siri` parses (case-insensitive), defaults to `apple`; an unknown value is a usage error naming the value (exit 1)
- [x] Engine selection sits behind one seam (`SpeechEngine.render(text:voice:rate:to:)`); `CLI`, `Assemble`, `Encode`, `ChapterMarkers` and `Brand` have no engine-specific code
- [x] Every private symbol reference lives in `Sources/SiriTTSBridge`, which exposes three C functions (`saybook_siri_probe`, `saybook_siri_synthesize`, `saybook_siri_free`)
- [x] Siri **Voices** are discovered from the macOS-delivered voice bundles, selectable by display name through the same selection logic as the public engine, and their absence is a readable user error naming the installed bundles
- [x] Engine output (48 kHz mono int16) is resampled into the package's CAF contract (22.05 kHz mono Float32) and a render whose frame count disagrees with the expected one is refused, because Chapter Marker offsets are computed from frame counts
- [x] The Scratch options marker carries `engine=`, so Chapters rendered by one engine are never reused as resume state for the other
- [x] `--rate` with `--engine siri` is refused rather than silently ignored
- [x] A run using the private engine says so in its progress header
- [x] Tests: plist parsing, unusable-engine reporting, a real render through the private engine (skipped on a Mac with no voice bundle), CLI exit codes, and an engine-switch invalidating cached Chapters
- [x] Docs: README (flag, the engine's caveats), ADR-0003, research notes under `.scratch/saybook/research/`

## Comments

- 2026-09-19 (agent): Started from the AFM 3 question — `.scratch/saybook/research/afm3-audio-generation.md`. AFM 3 (five models; the 20 B sparse **Core Advanced** one) does generate speech through an expressive-voice DiT detokenizer, but there is no API for it on this OS: `FoundationModels.swiftinterface` has zero audio/speech types, `AVSpeechSynthesis.h`'s newest marker is `macos(14.0)`, `say`/AVFoundation expose only the 180–185 legacy voices, and no `expressive` symbol exists in any public header. The only legitimate AFM 3 use today is generating SSML for an engine that *does* have an API. So the door had to be the private one: `.scratch/saybook/research/private-api-speech-synthesis.md`, with the runnable probe at `.scratch/saybook/prototype/siri-tts-probe.cpp`.
- 2026-09-19 (agent): Two doors exist, one closed. `com.apple.sirittsd` (LaunchAgent, `SiriTTSDaemonSession -synthesizeWithRequest:didFinish:`) refuses an unentitled CLI with `NSCocoaErrorDomain Code=4097 "connection to service named com.apple.sirittsd"` — and a bogus service name fails *differently* (`INVALIDATED`), which is what proves the 4097 is a real refusal rather than a missing service. The in-process `SiriTTS.framework` door is open: `TTSSynthesizer` exports 183 symbols (`xcrun dyld_info -exports`), and after `initialize(<AssetData dir>, "", "")` its `ready_for_synthesis()` returns 1 and `synthesize_text_sync` returned 263 640 bytes of PCM for one sentence. Chose the framework; `dlopen`/`dlsym` from a C++ bridge, no entitlement, no daemon.
- 2026-09-19 (agent): Four findings that each cost a debugging cycle, all now in the bridge's comments: (1) `dlsym` wants the Mach-O **leading underscore stripped** (`__ZN…` → `_ZN…`); with it left on, *every* lookup returns NULL, including `CFStringCreateWithCString`, which reads as "the framework is locked". (2) `initialize`'s third argument is a **persistent-module name, not a locale** — passing `"en-GB"` aborts with `std::logic_error: FrontendModuleBroker: Unknown module 'en-GB'`; an empty string is correct. (3) `available_neural_styles()` does **not** return `std::string` — calling it as one yields `Bus error: 10`, which looks like a crash in Apple's code and is not. (4) `timeout` does not exist on macOS, which produced several false-negative probe runs before the probes were restructured.
- 2026-09-19 (agent): Output format had to be pinned down from first-party evidence, because nothing announces it: the voice bundle's `gryphon.cfg` says `sample_rate_in: 24000`, `sample_rate_out: 48000`, `sample_rate: 48000`, and `+[SiriTTSNeuralUtils currentSampleRate:@"martha"]` reports 24 000 (the pre-vocoder stage). Float32 output is NaN — the buffer is signed 16-bit little-endian. Duration alone cannot disambiguate 48 kHz mono from 24 kHz stereo, so the check is against the public engine: the multi-chapter fixture renders 135.7 s through the Siri engine and 128.0 s through the public one (6% apart; a sample-rate error would be 2× off), and the assembled M4B is `1 ch, 22050 Hz, aac` at 135.7 s. Chapter CAFs read back as `1 ch, 22050 Hz, Float32` in `afinfo`.
- 2026-09-19 (agent): `AVAudioConverter` has two traps here, both caught by tests rather than by reading headers. (1) The Swift overlay's one-shot `convert(to:from:)` **rejects sample-rate conversion** with `OSStatus -50 paramErr`; the block-based `convert(to:error:withInputFrom:)` (`.haveData` once, then `.endOfStream`) works and lands 60 555 frames where 60 554 were expected. (2) Its output buffer must be at least as large as the *input* — an allocation sized for the downsampled result trips `required condition is false: outputBuffer.frameCapacity >= inputBuffer.frameLength`. The final code keeps `expected + 4096` with the block API and asserts the produced frame count against the expectation: a short render would silently drift every later Chapter Marker, so it fails instead.
- 2026-09-19 (agent): **The engine's logging can deadlock the CLI.** A `--engine siri` run hung in the suite with `synthesize_text_sync` blocked; `sample` showed the main thread inside `Diagnostics::log → vfprintf → __sflush → _swrite → __write_nocancel` — Apple's engine writes diagnostics to stdout/stderr from the calling thread, whatever `set_log_level` was given, and one 6-second Chapter produced **153 873 bytes** (2 739 lines). The test harness reads the child's pipes only after waiting, so once the 64 KB pipe buffer filled the child blocked forever; the same shape would bite any caller with `2>&1 | tee`. Fix is in the bridge, not the harness: `SilenceEngineLogging` `dup2`s `/dev/null` over both descriptors across every engine call and restores them afterwards (RAII, so an exception still unwinds cleanly), with `SAYBOOK_SIRI_DIAGNOSTICS=1` to opt back in for debugging. Verified: a Chapter's stderr goes from 153 873 bytes to 222 — saybook's own four progress lines — and the suite no longer hangs.
- 2026-09-19 (agent): Deliberate refusals. `--engine siri` **never falls back** to the public engine when it cannot render: a Book in an unrequested voice is worse than a failed run, and the Scratch marker plus frame-count guard mean the failure is loud, exit 1, with no output file and no half-written Chapter. `--rate` is refused for the same reason (the engine has no rate control) rather than accepted and dropped. Voice discovery has no `say -v ?` equivalent for a private engine, so the `--voice`/`--language` errors list the installed bundles instead of adding a `--list-voices` flag.
- 2026-09-19 (agent): Machine dependence is handled by skipping, not by weakening the tests. The voice bundles live under `/System/Library/AssetsV2/com_apple_MobileAsset_UAF_Siri_TextToSpeech` and macOS delivers them on its own schedule, so the tests that need a real voice (`a real render`, `a real CLI run`, `engine switch`) `XCTSkip` when the catalog is empty, while everything that can be decided from a plist is tested unconditionally through `SiriVoiceCatalog.describe` (made internal for exactly this). This Mac has one usable bundle (`martha`, `en-GB`, `EngineConfigTemplateType = fastspeech2_mil_base`); its `ProsodyTransferAssetPath`/`OrchestratorAssetPath` are empty and `isANEModelCompiled:` is still false — i.e. **this is not the AFM 3 expressive voice**, it is the ordinary Siri neural voice, and the plumbing to host one is there but the assets are not.
- 2026-09-19 (agent): Suite: **160 tests, 1 skipped, 1 failure** — `swift test` in 43.4 s and `swift test -c release` in 42.9 s, the README's both-configurations claim re-verified after this change (the new target compiles clean under `-O` with no warnings). The failure is **pre-existing and unrelated**: `CLITests.testBlocksAreSeparatedByAudiblePauses` expects 2 inter-Block silences and measures 3 (`0.53, 0.55, 0.22` s). Reproduced identically (same numbers) from a pristine `git worktree` at HEAD `18df32f`, so it is not from this ticket; it looks like a threshold artefact — the third run is 0.22 s against a `sampleRate/5` = 0.2 s floor. Left for whoever owns #05 rather than retuned here.
- 2026-09-19 (agent): Docs: ADR-0003 (`docs/adr/0003-private-siri-speech-engine.md`) records the decision, the rejected doors and the consequences (private API ⇒ not App-Store-eligible, unsupported by design); the README gains the `--engine` row, an honest `### The Siri engine` section (opt-in, no fallback, macOS-delivered voices, no rate control, breakable by any OS update, `SAYBOOK_SIRI_DIAGNOSTICS=1`), the engine in the Scratch-clearing rule and in Limitations, and the bridge in Layout. ADR-0001 is unchanged: it still describes the default engine.
- 2026-09-19 (agent): Post-resolution measurement, added to ADR-0003 and the README because the engine choice was undocumented on cost. Release binary, same fixture (2:16 of audio), M4: `--engine siri` **16.76 s wall / 400 474 112 B peak RSS**; `--engine apple` **3.24 s wall / 98 254 848 B** — 8.1× realtime against 39.5×, ~4× the memory. A 6-second Chapter renders in 1.10 s wall total, so the one-off voice load is under a second and the gap is render throughput, not startup. Extrapolated, a 10-hour Book is ~1¼ hours on the Siri engine against ADR-0001's ~11 minutes. Also confirmed on the release binary (the CLI test suite only ever runs the debug one): `afinfo` reports `m4bf`, 2:16, 553 KB.
